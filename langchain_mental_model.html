B · The Core Problem

What problem does LangChain solve?

Building real LLM applications requires far more than a single prompt and response. Every developer building on top of OpenAI or Claude was independently writing the same scaffolding: conversation memory management, document chunking and retrieval, output parsing from text to usable data structures, multi-step prompt pipelines, and external tool connections. This scaffolding was fragile, unreusable, and rebuilt from scratch for every new project.

LangChain packages all of that scaffolding into composable, battle-tested building blocks. It is not a smarter model. It is the operating system around the model — expanding what you can build without changing the model's underlying intelligence.

❌ Without LangChain — Ad-hoc

Custom glue code per project. Manual string concatenation for prompts. Manual JSON parsing on every LLM call. Custom memory management. No retrieval layer. Each project starts from zero. Fragile when LLM changes response phrasing.

✓ With LangChain — Systematic

Reusable Prompt Templates. Output Parsers that auto-convert text to data. Four memory strategies to choose from. Vector DB retrieval built-in. Chains for workflow composition. Agents for dynamic reasoning. Compose once, reuse forever.

The Key Reframe

The LLM is a brilliant consultant who works only in a single meeting room — zero memory between sessions, can only see what's on the table, cannot fetch external files. LangChain is the operating system around that consultant: bringing the right files into the room, injecting conversation history, routing questions to the right specialist, and stitching multi-step workflows together automatically.

C · The Complete Architecture

01 · User Input

A question, command, or document from the user. The entry point. Can be plain text, a structured form input, or a long document. This is the raw material everything else acts on.

→ Passed to Agent (if dynamic) or directly to Chain (if fixed workflow)
↓

02 · Agent — Dynamic Reasoning Engine

Uses the LLM as a reasoning engine that decides what to do next rather than following a fixed script. Implements the ReAct loop: Thought → Action → Observation → Thought → ... → Answer. The loop runs as many times as needed until the agent is confident it can answer.

Agents are used when the steps required to answer cannot be predetermined. If steps are known upfront, use a Chain instead.

→ Selects and calls Tools based on their plain-English descriptions
↓

03 · Tools — External Capabilities

Any function wrapped with a name and a plain-English description. The Agent reads descriptions to decide which tool to use and when. Built-in tools include web search, Wikipedia, and calculators. Custom tools wrap any API, database, CRM, or internal function you expose. The quality of the description determines the quality of tool usage.

Built-in: web_search, wikipedia, calculator · Custom: any wrapped function
↓

04 · Chains — Structured Workflows

LLM Chain: Atomic unit. One prompt + one LLM call = one output. The building block for everything else. Sequential Chain: Multiple LLM Chains in sequence. Simple variant passes single I/O down the line. Full variant allows any step to pull from any earlier step. Router Chain: LLM reads input and decides which subchain to route to — a smart switchboard using descriptions of each destination to route intelligently.

→ Output of one step automatically becomes input of the next. No manual piping.
↓

05 · Vector DB Retrieval — Document QA

Indexing (once upfront): Document → Chunking (mechanical splitting) → Embedding Model (converts each chunk to a vector of ~1500 numbers encoding meaning) → Vector Database. Retrieval (every query): Question → Embed → Compare against all chunk vectors → Return top-k most semantically similar chunks → Feed to LLM.

Embeddings encode meaning, not words. "The puppy ran after the sphere" and "The dog chased the ball" produce numerically close vectors despite sharing zero words. This semantic search finds relevance that keyword search misses entirely.

Retrieval methods: Stuff · Map Reduce · Refine · Map Rerank
↓

06 · Memory — Conversation Continuity

LLMs are completely stateless. Every API call is a blank slate. "Memory" is an illusion — conversation history is injected into every new prompt behind the scenes. Four strategies manage the cost/detail tradeoff: Buffer (keep all), Window (keep last k), Token Buffer (keep to token limit), Summary (LLM compresses history). Production apps combine strategies for different needs.

Injected as context into every new prompt call
↓

07 · Prompt Templates — Structured Input

Prompts with named variable slots defined once, reused forever. Instead of manually concatenating strings, you declare a structure and fill slots. Prompt Templates and Output Parsers are designed as a coupled pair — the Parser tells the Template exactly what instructions to embed so the LLM responds in a format the Parser can reliably process.

→ Sent to the LLM as a formatted prompt
↓

08 · LLM — The Model

The language model itself (GPT-4, Claude, etc.). Always returns plain text. Always. No exceptions. Even when the response looks exactly like JSON, it is 38 characters of plain text — not a data structure. The LLM describes data; it does not hand you data. Treat every LLM response as a photograph of information, not the information itself.

→ Returns text to the Output Parser
↓

09 · Output Parser — Text → Usable Data

Converts the LLM's text response into a real data structure the application can act on. Like converting a photograph of a filing cabinet into an actual cabinet with openable drawers. Before parsing: `response["is_gift"]` crashes because response is a string. After parsing: `response["is_gift"]` returns `True` — the drawer opens. Without a parser, apps must write fragile custom text-extraction code that breaks whenever the LLM slightly changes phrasing.

→ Returns dictionary / structured data to the application
↓

10 · Evaluation Layer

LLM outputs cannot be verified by exact string matching — infinite valid phrasings exist for every correct answer. LangChain uses a second LLM (the Eval Chain) to grade outputs semantically. Pipeline: generate Q&A test pairs (manually or auto-generated) → run QA chain → Eval LLM grades correct/incorrect. The debug layer (`langchain.debug`) exposes every internal step: exact prompt sent, chunks retrieved, tokens used, raw output before parsing.

Key insight: wrong answers almost always = bad retrieval, not bad LLM
D · Failure Modes

Photograph vs. Cabinet — Missing Output Parser

The LLM returns text that looks like JSON. The application tries to access a key: `response["is_gift"]`. The app crashes. No error in the LLM — it did exactly what was asked. The failure is in assuming text = data structure. The LLM always returns a string. Always. The parser was skipped.

MODULE 2 SILENT UNTIL RUNTIME Prevention: Always pair Prompt Template with Output Parser

Context Window Breach — Memory Unbounded

Buffer Memory keeps the entire conversation verbatim. A long support conversation eventually exceeds the LLM's maximum token window. Oldest messages are silently dropped. The model now cannot see critical information mentioned early in the conversation. User says "the first issue I mentioned" — the LLM has no memory of it. No error fires. Answers become subtly wrong.

MODULE 3 SILENT Prevention: Use Window, Token Buffer, or Summary Memory for long conversations

Detail Loss in Summary Memory

Summary Memory uses an LLM to compress conversation history. LLMs summarise by compressing — specific details quietly disappear. A case number, exact date, specific clause, or precise figure mentioned early in the conversation survives human note-taking but evaporates in AI summarisation. Application appears to work but gives subtly wrong answers referencing lost details.

MODULE 3 SILENT Prevention: Combine Summary Memory with explicit key-fact store for critical details

Key Name Mismatch — Sequential Chain Crash

Sequential Chain requires exact matching of output key names to input key names across steps. Step 2 outputs `english_review`. Step 3 expects `englishReview`. Hard crash. No graceful degradation. This failure is particularly common when chains are assembled from components built at different times.

MODULE 4 NON-SILENT — HARD CRASH Prevention: Define and document all key names before wiring steps together

Wrong Chunks Retrieved — Silent Wrong Answers

The most common failure in document QA. Chunks about pricing are retrieved for architecture questions because the embedding similarity is high enough to pass the threshold but semantically misaligned. The LLM generates a confident, well-structured answer — based entirely on the wrong context. No error fires. The answer looks correct until a domain expert reviews it.

MODULE 5 SILENT — MOST DANGEROUS Prevention: Smaller focused chunks, debug layer inspection, evaluation pipeline

Token Window Overload — Stuff Method Fails

The Stuff retrieval method feeds all retrieved chunks into one prompt. For complex documents requiring 10+ chunks, this exceeds the token window. The LLM either truncates context silently or the API call fails. The application either crashes or produces answers based on incomplete context with no indication of which.

MODULE 5 SILENT TRUNCATION OR HARD CRASH Prevention: Use Map Reduce or Refine for large document sets

Exact Match Evaluation — False Failures

Automated evaluation using string matching marks semantically correct answers as incorrect. Ground truth: "Yes". LLM answer: "Based on the documentation, water damage is indeed covered." String match returns False. System reports 0% accuracy on questions it answered correctly. Engineering team chases a non-existent problem.

MODULE 6 NON-SILENT — MISLEADING METRICS Prevention: Always use LLM-as-evaluator (Eval Chain), never exact string matching

Agent Mid-Loop Failure — Non-Determinism

An agent searching for current information concludes mid-loop that an event "hasn't happened yet" — then corrects itself after an additional search. On identical inputs, agents may take different paths, use different tools, or reach different conclusions. In high-stakes applications (legal, medical, financial) this non-determinism produces unreliable outputs without any error signal.

MODULE 7 SILENT — INCONSISTENT OUTPUTS Prevention: Guardrails + human-in-the-loop checkpoints + bounded tool access for high-stakes cases

Bad Tool Description — Tool Ignored or Misused

An Agent decides which tool to use by reading the plain-English description of each tool. A vague or poorly written description causes the agent to ignore a relevant tool entirely or call it with the wrong input. The agent proceeds without the data it needed — producing confidently wrong answers with no error.

MODULE 7 SILENT Prevention: Write precise, specific tool descriptions including exact input format requirements

F · Decision Heuristics
RULE 01

If you know all the steps upfront — use a Chain. If the steps depend on what the question requires — use an Agent. Never use an Agent when a Chain will do. Agents introduce non-determinism that Chains avoid entirely.

RULE 02

Every LLM response is a string. Always. Never assume the output is JSON, a list, or any other type. If your app needs structured data, an Output Parser is mandatory — not optional. No exceptions.

RULE 03

Wrong answer = bad retrieval, not bad LLM. When a QA system returns incorrect answers, inspect the retrieved chunks before touching the prompt or the model. 80% of the time, the wrong chunks were fetched. Fix retrieval first.

RULE 04

Never evaluate LLM output with exact string matching. Always use an Eval Chain (LLM-as-evaluator) for semantic grading. Exact matching marks correct answers as failures and produces meaningless accuracy metrics.

RULE 05

For synthesis across multiple sections — use Refine, not Stuff. Stuff breaks at scale. Map Reduce misses cross-section dependencies. Refine builds context iteratively — the only method that accumulates understanding across interconnected sections.

RULE 06

High-stakes applications never use Summary Memory alone. Always pair it with an explicit key-fact store for critical details (case numbers, dates, specific figures). LLM summaries silently drop precision — your application cannot tell what was lost.

RULE 07

Tool descriptions are as important as tool logic. An Agent with a perfectly coded tool but a vague description will ignore the tool entirely. Write descriptions as instructions to the LLM: what the tool does, when to use it, what exact format the input must be.

RULE 08

If routing is needed — use a Router Chain, not conditional code. Encoding routing logic as if/else in application code breaks every time a new category is added. Router Chain uses LLM to decide dynamically — add a new destination by adding a description, not rewriting code.

RULE 09

Smaller chunks = better retrieval precision. Chunks that mix multiple topics produce vectors representing nothing well. Each chunk should cover exactly one concept so its vector cleanly represents that concept's meaning space.

RULE 10

Production apps combine memory strategies. No single memory type handles all requirements. Use Summary Memory for conversation flow + Buffer or explicit store for facts that must never be lost. Design memory architecture like you design a database schema.

H · Terminology Glossary
Agent
A LangChain component that uses an LLM as a dynamic reasoning engine, deciding which tools to call and in what order at runtime rather than following a fixed path.
Chain
A sequence of LLM operations where the output of one step automatically becomes the input of the next, following a fixed path defined before execution.
Chunking
The mechanical process of splitting a large document into smaller text segments before embedding. No AI involved — purely a splitting operation.
Embedding
The conversion of text into a vector (list of ~1500 numbers) that encodes semantic meaning. Semantically similar text produces numerically close vectors.
Eval Chain
A LangChain component that uses an LLM to evaluate another LLM's output, judging semantic correctness rather than exact string match.
LLM Chain
The atomic building block of LangChain — a single Prompt Template combined with a single LLM call producing a single output.
Map Reduce
A retrieval method that processes each document chunk independently in parallel (map), then synthesises all individual answers into a final response (reduce).
Output Parser
A LangChain component that converts the LLM's plain text response into a usable data structure (dictionary, list, etc.) that the application can act on programmatically.
Prompt Template
A reusable prompt structure with named variable slots. Defined once, reused by filling slots with different inputs — eliminates manual string concatenation.
ReAct Loop
The Agent reasoning pattern: Thought (what do I need?) → Action (use a tool) → Observation (what did I get?) → repeat until the agent can answer confidently.
Refine
A retrieval method that processes chunks sequentially, each iteration building on the previous answer — best for complex synthesis where sections reference each other.
Retrieval QA
The pattern of embedding documents, storing vectors, retrieving top-k semantically similar chunks on each query, and passing those chunks to an LLM to generate a grounded answer.
Router Chain
A chain type that uses an LLM to read input and decide which specialist subchain to route it to, based on plain-English descriptions of each destination.
Stateless
The property of LLMs where every API call starts with zero memory of previous calls. Each request is completely independent — the model has no inherent continuity.
Stuff Method
The simplest retrieval method: all retrieved chunks are combined into one prompt and sent in a single LLM call. Fast but fails when chunks exceed the token window.
Tool
Any function wrapped with a name and plain-English description that an Agent can call. The description tells the LLM when and how to use it — quality of description determines quality of tool usage.
Token Window
The hard maximum limit on how much text an LLM can process in a single call. Exceeding this limit causes content to be silently truncated or the API call to fail.
Vector Database
A database that stores vectors (numerical representations of text meaning) and supports semantic similarity search — finding documents by meaning, not exact keyword match.
