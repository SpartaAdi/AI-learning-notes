AThe Core Problem

The problem this domain solves: LLM products plateau — and fail silently — when teams change behavior (prompts, fine-tuning, code) without a system to measure whether that change actually helped. Ad-hoc "vibe checks" cannot scale past a single person's working memory, and once product surface area grows, fixing one failure mode surfaces another (whack-a-mole) with no way to know if net quality improved.

The key reframe: Evaluation is not a QA checkpoint bolted onto the end of development — it is the mechanism that makes debugging and iteration possible at all. The eval system, the debugging infrastructure, and the fine-tuning data pipeline are, structurally, the same system.

Naive Approach

Track generic scores (helpfulness, coherence, toxicity) on a 1–5 scale. Pick metrics before looking at any real data. Delegate annotation to outsourced labelers or committees. Treat AI roadmaps like feature roadmaps with fixed ship dates.

Systematic Approach

Read raw traces first (open coding), let failure categories emerge (axial coding), build binary pass/fail evaluators validated against one domain expert's judgment, and structure roadmaps around experiment cadence rather than deadlines.

BThe Complete Pipeline

Stage 1

Trace Collection

Every user interaction — messages, tool calls, retrievals, intermediate steps — logged as a complete trace. If no real users exist yet, generate synthetic traces using structured dimensions (Features × Scenarios × Personas) rather than free-form LLM prompting.

Produces: raw material for error analysis. Connects to → Stage 2 via manual review.
↓
Stage 2

Open Coding

A single domain expert ("benevolent dictator") reads raw traces with zero predefined categories and writes free-form notes on anything wrong. No taxonomy imposed yet — the goal is discovery, not classification.

Captures: undiscovered failure patterns. Connects to → Stage 3 once ~30-50 traces reviewed.
↓
Stage 3

Axial Coding

Group open-coding notes into a named failure taxonomy; count frequency per category. Continue until theoretical saturation (~100 traces reviewed, no new category in the last ~20). LLMs may draft groupings after human open coding — never before, never unsupervised.

Decides: which failure modes are worth building evaluators for. Connects to → Stage 4.
↓
Stage 4

Binary Judgment + Critique (Critique Shadowing)

Domain expert makes a pass/fail call per trace plus a detailed critique explaining reasoning. This step exists because criteria drift makes it impossible to define evaluation criteria before seeing real outputs — grading is what surfaces the actual standard.

Produces: labeled ground truth + few-shot material. Connects to → Stage 5.
↓
Stage 5

LLM-as-Judge Construction

Build a judge prompt using the expert's actual critiques as few-shot examples. Iterate until agreement (measured via TPR/TNR, not raw agreement if classes are imbalanced) exceeds ~90%. Never fine-tune the judge by default — prefer prompt iteration.

Key primitive: few-shot critique examples, not abstract instructions. Connects to → Stage 6.
↓
Stage 6

Deployment: CI/CD vs. Production

CI/CD: small curated datasets with known reference answers → cheap deterministic assertions, run every commit. Production: sampled live traffic with no reference answer → reference-free LLM-judge, run asynchronously on a subset.

APIs/patterns: guardrails (synchronous, fast, deterministic) vs. evaluators (asynchronous, judgment-based). Connects to → Stage 7.
↓
Stage 7

Feedback Loop

New failure patterns discovered in production become new CI test cases. Roadmap operates on experiment cadence (fixed check-in intervals + pivot/ship decision points), not fixed feature-ship dates — because AI progress is not reliably time-boxable.

Closes the loop back to → Stage 2 (re-run error analysis on fresh traces every 2-4 weeks).

CSilent & Non-Silent Failure Modes

Module 1

Whack-a-Mole Plateau

What happens: Fixing one visible failure causes an unrelated one to surface elsewhere; net quality may be flat or worse. Why no error fires: without systematic tracing, there's no signal connecting the fix to a regression elsewhere. Prevention: Build the eval/debug loop before scaling prompt changes.

Module 3

Premature Categorization

What happens: Picking failure categories (e.g. "hallucination rate") before reading raw data causes real failure patterns (e.g. date-parsing bugs) to be ignored or misfiled into the wrong bucket. Why no error fires: the metric reports a clean number even while missing the actual problem entirely. Prevention: Open code first; only categorize after saturation.

Module 3

LLM Taxonomy Merge Error

What happens: An LLM asked to build a failure taxonomy merges distinct failure types (e.g. "app crashes after login" + "login is slow") into one bucket ("login issues") because they're linguistically similar. Why no error fires: the taxonomy looks coherent and complete. Prevention: Human must validate every LLM-drafted taxonomy before use.

Module 6

Generic Metric Drift

What happens: A proxy score (e.g. "helpfulness: 3.4→3.7") rises while real task success stays flat, because the metric rewards tone/format/politeness rather than task completion. Why no error fires: the dashboard shows genuine upward movement — it's measuring the wrong thing, not malfunctioning. Prevention: Derive all metrics from error analysis on your own data; never adopt off-the-shelf generic scores as primary signal.

Module 7

Committee Ground-Truth Noise

What happens: Multiple annotators disagree on the same trace; whichever label lands in the training set becomes "ground truth" arbitrarily. Why no error fires: the dataset looks fully labeled — inconsistency is invisible unless inter-annotator agreement is explicitly measured. Prevention: Single domain expert by default; Cohen's Kappa + alignment sessions only if multiple annotators are unavoidable.

Module 9

Blended RAG Score Masking

What happens: A single quality score blends retrieval correctness and generation quality; a low score can't reveal whether the problem is "wrong documents found" or "right documents used poorly." Why no error fires: the score reports clearly — just not usefully. Prevention: Score retrieval (IR metrics: Recall@k, Precision@k, MRR) and generation (LLM-judge) separately.

Module 10

Feature-Roadmap False Failure

What happens: A project is killed at a fixed deadline because "nothing worked yet" — even when a breakthrough was weeks away. Why no error fires: the roadmap's only signal is elapsed time vs. deadline, which cannot distinguish "unsolvable" from "not yet solved." Prevention: Replace ship-dates with experiment cadence + explicit pivot/ship decision points.

EDecision Heuristics

Saturation Rule

Review at least 100 traces before drawing conclusions; stop discovering new categories if the last ~20 traces reveal nothing new.

One Expert Rule

Default to a single domain expert ("benevolent dictator") as final judgment authority — needing 5 experts to agree signals your product scope is too broad.

Binary-First Rule

Always start with pass/fail judgments plus critique. Only add numeric granularity for specific sub-components, never as a replacement for the binary call.

Fix-Before-Build Rule

Fix obvious, cheap-to-catch errors before investing in an LLM-as-judge. Reserve judges for failures that persist after obvious fixes.

Validity-Density Rule

Use cross-product generation when most dimension combinations are valid; use direct LLM generation when many combinations would be nonsensical.

Reference-Availability Rule

If a correct answer is knowable in advance, use deterministic assertions. If not, use a reference-free LLM-judge.

Agent Two-Phase Rule

Evaluate agents end-to-end (task success) first via error analysis; only build step-level transition matrices for the workflows error analysis flags as high-failure.

Experiment Cadence Rule

Replace fixed ship-dates with fixed check-in intervals and explicit pivot/ship decision points for any AI roadmap item with real technical uncertainty.

GTerminology Glossary

TermDefinition
TraceComplete record of all actions, messages, tool calls, and retrievals from one user query through to final response.
Open CodingReading raw traces and writing free-form notes on failures without any predefined category.
Axial CodingGrouping open-coding notes into a named failure taxonomy and counting frequency per category.
Theoretical SaturationThe point at which reviewing more traces stops revealing new failure categories.
Criteria DriftThe phenomenon where evaluation criteria only become fully defined through the act of grading real outputs — they cannot be fully specified in advance.
Critique ShadowingThe 7-step process of building an LLM judge by first collecting domain-expert pass/fail judgments with critiques, then using those as few-shot examples.
Benevolent DictatorThe single domain expert whose judgment is treated as ground truth for a given evaluation domain.
GuardrailA fast, deterministic, synchronous check that blocks or corrects output before it reaches the user.
EvaluatorAn asynchronous, judgment-based check that measures quality after a response is produced, without blocking it.
Recall@k / Precision@k / MRRInformation-retrieval metrics for RAG retrieval quality: how many relevant docs were found in the top k, how many retrieved docs were relevant, and how high the first relevant doc ranked.
Transition Failure MatrixA matrix mapping last-successful-state to first-failure-state in an agentic workflow, used to locate failure hotspots.
Capability FunnelA framework breaking AI performance into progressive levels of utility, from basic functionality to complete solution.
Experiment-Based RoadmapA roadmap structured around a fixed cadence of experimentation and check-ins rather than fixed feature-ship dates.
