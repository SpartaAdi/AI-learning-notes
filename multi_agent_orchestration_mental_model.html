B. The Core Problem

What it solves: A single agent with more tools does not scale to multi-domain tasks. As task complexity grows (e.g. a cancelled connecting flight touching refund policy, hotel reimbursement, and a different airline's compensation rules), a single ReAct loop must reason about all of it in one growing, shared context.

Why naive approaches fail: One flat trajectory means context dilution (attention split across unrelated policy domains), error compounding (an early mistake pollutes all later reasoning in the same trajectory), and no specialization (one agent prompted/tooled to be a generalist is worse at each sub-task than a purpose-built agent).

Key insight: Multi-agent design is not about tool coverage — it is about isolating reasoning contexts so each agent stays sharp on one domain, and introducing an orchestration layer to recombine specialized outputs correctly.

Naive Approach

One agent, many tools, one flat context handles every sub-domain of a complex task in a single trajectory.

Systematic Approach

Specialized agents per domain, each with its own isolated context, coordinated by an orchestration layer that manages control flow and shared state.

C. The Complete Architecture

1. Nodes

A unit of work in the graph — a function or an agent (e.g. Refund Agent, Hotel Agent, Router, Synthesizer). A node reads current shared state, does its work, and returns an update to that state.

Connects to →

Edges determine which node executes next after this one completes.

2. Edges

Legal transitions between nodes. Can be fixed (always A→B) or conditional — a function that inspects current state and decides which node runs next, evaluated fresh every time it fires. Edges are the only way execution moves; persistent state does not itself grant any node the ability to trigger another.

Connects to →

Conditional edges are what make cycles (deliberate loops/retries) possible — something a linear chain structurally cannot do.

3. Shared State

A single structured object every node reads from and writes to. Unlike a LangChain chain — where each node's output is the next node's input and then disappears — graph state persists and accumulates across the entire run. Any node can see what any earlier node wrote.

Key primitive: Reducers

A reducer defines how a new write to a field combines with the existing value: overwrite (default, last-write-wins — correct only for single-writer fields like booking_id), append (for running logs like messages — every agent's contribution preserved), sum (for numeric accumulators like total_compensation).

4. Orchestration Pattern (topology)

Supervisor — one central node sees full state, decides which sub-agent(s) run, receives output, decides next step. Centralized, auditable. Hierarchical — nested supervisors; each team-lead node manages its own local sub-state, absorbing and compressing its team's output before passing a summary upward — solves context bloat at scale via state encapsulation. Network — no central authority; any agent can hand off to any other based on its own judgment. Flexible but no built-in termination or accountability guarantee.

5. Handoff Mechanism

There is no direct agent-to-agent message channel. "Handoff" concretely means: Agent A returns an update → the reducer attached to each touched field merges it into shared state → the edge routes to the next node → that node reads the resulting state. Everything is mediated through state, never passed directly.

6. Checkpoints & Recursion Limits

State is persisted (checkpointed) after each node completes successfully — node execution is atomic with respect to state: a crash mid-node writes nothing, so partial in-state writes don't occur. Recovery means re-running the failed node against the last good checkpoint. A recursion limit caps total steps to force termination even if a conditional edge's loop logic never resolves cleanly.

D. Silent & Non-Silent Failure Modes

State Field Collision (Overwrite on shared field)

What happens: Two agents write to the same state field (e.g. both write to total_compensation) without a reducer; the last write silently replaces the first.

Why no error fires: The write succeeds mechanically — there's no type or logic violation, just lost data.

Prevention rule

Use separate fields per writer, or attach a sum/append reducer to any field multiple agents write to.

Overwrite Reducer on a Log Field

What happens: A running history field (e.g. messages) uses an overwrite reducer instead of append; every prior agent's reasoning, tool calls, and flags vanish the moment the next agent writes.

Why no error fires: The graph completes normally and produces an answer — it just runs on incomplete information, and there's no trail left to detect it.

Prevention rule

Any field meant to hold accumulated history must use an append reducer, never overwrite. Treat log/audit fields as append-only by default.

Runaway / Infinite Cycle

What happens: A conditional edge's exit condition is buggy (e.g. never detects "enough info gathered"), so the graph loops between nodes indefinitely.

Why no error fires: Each loop iteration is a valid, successful transition — nothing is technically wrong per-step, only in aggregate.

Prevention rule

Always set a recursion limit as a hard backstop, independent of trusting the loop-exit logic to be correct.

Side-Effect Non-Idempotency on Retry

What happens: A node performs a real-world action (e.g. calls a payment API to issue a refund) then crashes before returning its state update. Checkpointing recovery re-runs the entire node — re-triggering the real-world action a second time.

Why no error fires: LangGraph's state atomicity guarantee is real (no partial state writes) — but it says nothing about external side effects, so the retry looks like normal, successful recovery.

Prevention rule

For any node with an external side effect, implement idempotency keys (e.g. check "has a refund already been issued for this complaint ID?" against an external record) before acting — state-level atomicity ≠ real-world action atomicity.

F. Decision Heuristics

If a task spans more than one distinct knowledge/tool domain, split into specialized agents rather than adding tools to one agent.

Default every state field to overwrite only if you're certain exactly one agent will ever write it — otherwise pick a reducer explicitly.

Any running log/history/audit-trail field must use append, never overwrite — this is a silent-failure trap.

Choose Supervisor/Hierarchical over Network whenever the system needs auditability or regulatory accountability.

Switch flat Supervisor to Hierarchical once agent count grows large enough that the Router's context is bloated with raw sub-agent output.

Every conditional edge that enables a cycle needs a recursion limit as a backstop — never trust loop-exit logic alone.

Any node with a real-world side effect (payment, email, booking) needs an idempotency check — checkpointing does not protect against duplicate side effects on retry.

Design the Synthesizer/aggregation node explicitly — don't rely on a shared field to "just add up" without a reducer or explicit aggregation logic.

H. Terminology Glossary

Node
A unit of work in a graph (function or agent) that reads state and returns an update.
Edge
A legal transition between nodes; fixed or conditional.
Conditional edge
An edge governed by a function that inspects state and picks the next node dynamically, evaluated on every firing.
Shared state
A persistent structured object all nodes read from and write to across the entire graph run.
Reducer
A rule attached to a state field defining how new writes combine with the existing value (overwrite, append, sum, etc.).
Handoff
The mediated transfer of information between agents via state update + reducer + edge — never a direct message.
Supervisor pattern
Centralized orchestration — one node sees full state and decides all routing.
Hierarchical pattern
Nested supervisors, each managing a local sub-state, passing summarized results upward.
Network pattern
Decentralized orchestration — any agent can hand off directly to any other, no central authority.
Cycle
A graph path that revisits an earlier node (e.g. A→B→A), enabling deliberate retries/loops — impossible in a linear chain.
Recursion limit
A hard cap on total graph steps, forcing termination even if loop-exit logic never resolves.
Checkpoint
Persisted state snapshot saved after each node's successful completion, enabling resume-from-last-good-state on failure.
State atomicity
Guarantee that a node's state update is committed only if the node completes successfully — no partial writes.
Idempotency
Property ensuring a real-world action (e.g. issuing a refund) has the same effect whether performed once or retried multiple times; not provided automatically by LangGraph.
