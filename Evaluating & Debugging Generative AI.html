Part 1 — The Core Problem W&B Solves

The Five Things That Must Be Captured to Reproduce Any Experiment

Without all five, the experiment cannot be reliably reproduced — even weeks later, on the same machine, by the same engineer.

1. Hyperparameters

Learning rate, batch size, dropout, epochs. Easy to write down — rarely written down reliably.

2. Base model version

Which pre-trained model was used, and which version. Recoverable if the model hub is versioned properly.

3. Dataset version

Which data was used to train. Hard to recover if no tagging discipline exists. One of the most commonly missed.

4. Code state ⚠

The exact script at the moment of the run. Nearly impossible to recover from a modified notebook never committed to Git.

5. Environment ⚠

Library versions, CUDA version, OS. Almost never recorded manually. A version mismatch silently changes results.

What Git covers: Code state only — and only if every change is committed. W&B covers all five automatically, every run, with zero manual discipline required. It also captures a diff patch of any uncommitted code changes, so even untracked notebook edits are preserved.

Part 2 — The W&B Pipeline (8 Layers)

Each layer builds on the previous. Skipping any layer breaks the chain — the next layer cannot compensate for a gap earlier in the flow.

1
Training Script
The entry point. All five reproducibility components live here: the model definition, hyperparameters, dataset loading, training loop, and the environment it runs in. Nothing is tracked yet — this is the raw state before instrumentation begins.
Code + config Dataset loader Training loop Environment
2
Instrumentation — Three Lifecycle Hooks
W&B integrates with just three additions to any training script. No restructuring required. The hooks bind to the natural lifecycle of a training run: before, during, and after.
wandb.init()Called once before training. Passes project name + config dict. Captures code state, environment, Git hash, diff patch.
wandb.log()Called repeatedly inside the training loop — at every step or epoch. Streams metrics in real time: loss, accuracy, learning rate, custom metrics.
wandb.finish()Called once after training ends. Seals the run cleanly. Required in notebooks.
Auto-captures diff patch Auto-captures environment Real-time streaming
3
Run — The Atomic Unit
One Run = one experiment = one configuration executed once. The Run is the permanent, sealed record of a single training attempt. Everything W&B captures is bound to the Run — it cannot be changed after finish() is called.

Config (static)

Set once at init(). Answers: "What did we try?"
E.g. learning_rate: 0.001, epochs: 10, dropout: 0.3

Metrics (dynamic)

Streamed in loop via log(). Answers: "What happened?"
E.g. loss at step 200: 0.43, val_accuracy: 0.91

The Project layer: A project is a collection of runs. The project dashboard lets you compare all runs on one chart, filter by threshold, sort by any metric, and surface the best experiment instantly — without digging through notebooks.

4
Artifacts — Version Control for Everything Produced
An Artifact is not just a saved file. It is a versioned, context-bound object with a permanent link back to the Run that produced it. This link is called lineage — the traceable chain from output back to input, code, and training configuration.

🤖 Model checkpoints

Saved every N epochs. Enables crash recovery, overfitting protection (best epoch may not be last), and branching.

📦 Datasets

Versioned training inputs. Know exactly which data produced which model. Essential for the data→output feedback loop.

📊 Predictions

Outputs logged for evaluation. Can include images, text, or any rich media alongside numeric scores.

💻 Code

Including the diff patch for uncommitted changes. Reproduce any run: pull Git commit + apply patch.

Why not just use S3? An S3 file is an orphan — it has no context. You cannot answer: which run made this? What dataset? What code? What metrics did it achieve? W&B Artifacts answer all of these automatically through lineage graphs.

5

This deliberateness is the feature — it forces a conscious quality judgment before any model enters the deployment lifecycle.

6
Tables — Rich Evaluation & Visual Comparison
A Table is a rich, interactive data frame where cells can contain images, text, audio, video, or molecules — not just numbers. Tables answer the question "What does the output actually look like?" across many runs or methods at once.

The Sampler Battle Pattern (generalised A/B evaluation)

Same input → Method A output → Method B output → judgment column. Works for: two sampling algorithms, two prompt templates, two fine-tuned variants, two RAG retrieval strategies. Any time you want to isolate one variable and compare outputs, this is the template.

7
Tracer — Step-by-Step Execution Observability
Tables show you what was produced. Tracer shows you how and why it was produced — step by step. Essential for LLM chains and agents where: (1) the wrong output gives no information about which step failed, and (2) failures are non-deterministic and may not reproduce reliably.

Span

One recorded step: input, output, start time, end time, success/failure status. The unit of observability for each action in a chain or agent.

Trace

The full nested record of all spans in one end-to-end execution. The trace timeline shows exactly where execution went wrong — even if the final output looked valid.

Chain vs Agent — Critical Distinction

Chain

Steps are fixed and predetermined. Always runs 1→2→3. Predictable. Easier to debug. Use for known, stable workflows.

Agent

The LLM decides which steps to run and in what order at runtime. Dynamic, more powerful, harder to debug. Always requires a Tracer in production.

8
Human Judgment — Qualitative Evaluation
The final layer that no tool can replace. For generative models, loss going down only means the model got better at predicting the next token — not that the output is coherent, accurate, stylistically correct, or useful. You must read actual outputs.

The Qualitative Evaluation Workflow

Fine-tuning complete → generate sample outputs across diverse prompts → log to W&B Table → read them, actually read them → observe failure patterns (repetition, truncation, wrong tone, missing sections) → design task-specific metrics that quantify those patterns → log custom metrics + outputs together → next iteration.

"Tools create the conditions for judgment. They do not replace it."

Part 3 — Why Generative Models Need Different Monitoring

Supervised model

Loss → qualityReliable relationship throughout training
Primary signalLoss + accuracy metrics
EvaluationQuantitative only — metrics tell the full story
Stop conditionWhen metrics plateau

Generative model

Loss → qualityUnreliable — loss flattens early, quality keeps improving
Primary signalVisual or text sample inspection at regular intervals
EvaluationQualitative required — metrics alone miss the failures
Stop conditionWhen outputs are acceptable — not when loss plateaus

Generative model monitoring checklist

  • Loss curve — Is it going down at all? Basic health check only — not a quality signal.
  • Generated samples at regular intervals — Log actual outputs (images or text) at every N epochs. Watch them evolve visually.
  • Sample diversity — Is the model generating varied outputs, or collapsing to repetition loops?
  • Baseline comparison — Log epoch 1 outputs so you have a reference point for improvement over time.
  • Checkpoints at every N epochs — The best-performing model is often not the final one. You need to recover mid-training states.

Part 4 — Fine-Tuning vs RAG vs Training from Scratch

Training from scratch

Build a new model entirely from random initialisation. Almost never justified — requires massive compute, data, and time.

When: unique architecture needed

RAG (Retrieval Augmented Generation)

Keep existing model weights unchanged. Retrieve relevant documents from a knowledge base and inject them as context at query time.

When: model lacks information — missing facts, current data, private documents

Fine-tuning

Continue training a pre-trained model on your specific dataset. The model already knows language — you are teaching it a specialisation. Knowledge gets baked into weights.

When: model lacks behaviour — wrong style, tone, format, or domain instinct

The key diagnostic question

Ask: "Does the model lack information, or does it lack the right behaviour?" RAG answers information gaps. Fine-tuning answers behaviour gaps. Production systems for specialised domains often need both: RAG for specific facts, fine-tuning for the correct output style.

Minfy example: Client onboarding docs for AWS engineers. RAG handles "what are our internal tools?" (information). Fine-tuning handles "write exactly the way our senior engineers write" (behaviour).

Part 5 — Six Silent Failure Modes

Silent failures share one property: no error is thrown, no alarm fires, and the system reports success while producing wrong results. These are the most dangerous failures in ML systems.

Module 3 — Artifacts
1. Orphaned Artifact
A model file is saved to S3 or disk without any W&B linkage. The file exists, the metrics exist — somewhere — but there is no traceable connection between them. Six weeks later, when asked "which dataset trained this production model?", nobody can answer. The lineage chain is broken at the save step.
Prevention: always log model saves as W&B Artifacts, never as bare file writes.
Module 4 — Diffusion Model Monitoring
2. Loss Convergence Trap
Training is stopped because loss has flattened and appears to have converged. For a generative model, output quality may still be improving significantly at this point — loss and quality diverge early in training. The model is declared done and shipped. The images or text it generates are blurry, noisy, or incoherent. No error was thrown during training.
Prevention: log sample outputs at regular intervals throughout training; inspect them, not just the loss curve.
Module 5 — Model Registry
3. Registry Discipline Skip
Under deadline pressure, the team deploys a model artifact directly without promoting it through the Registry. Artifacts exist and are versioned. But six months later, when the production model degrades, nobody can identify which artifact version is running, what training run produced it, or what its performance history was. The governance layer was never used, so the traceability it provides does not exist.
Prevention: treat Registry promotion as a non-negotiable gate, not an optional step — enforce this in team process.
Module 7 — LLM Evaluation & Chain Tracing
4. Agent None Pass-Through
An agent is given a multi-step task: pick a world, generate a hero name, validate the name. The agent reasons through step 1 correctly but skips step 2 (name generation) and jumps directly to step 3 (validation). The validator receives None as the name — but None is technically under 20 characters, so it passes the validation rule. The agent reports success. The output is wrong. No error was thrown at any step.
Prevention: use Tracer to inspect every span in the execution timeline — the bug is visible in the trace, invisible in the output.
Module 8 — Fine-Tuning & Qualitative Evaluation
5. Fine-Tune Without Reading Outputs
A model is fine-tuned on a specific dataset. Loss goes down cleanly over training. The model is promoted to the Registry and deployed. Nobody reads the actual generated text. In production, the model enters repetition loops: "the tribe of the tribe of the tribe of the tribe." The metric (loss) looked healthy. The behaviour was broken. The failure was invisible to every quantitative measure.
Prevention: read generated outputs across diverse prompts before any promotion. Loss going down ≠ output quality.
Module 8 — Fine-Tuning & Qualitative Evaluation
6. Metrics Without Judgment
The full W&B pipeline is used correctly. Runs tracked, Artifacts versioned, Registry updated, Tables populated. Every tool functioned as designed. But the team never actually inspected the outputs — they trusted the metrics as a proxy for quality. The qualitative evaluation step was skipped. The system worked. The product failed. This is the highest-level failure mode: correct tooling, missing judgment.
Prevention: qualitative evaluation is not optional for generative AI — design task-specific failure metrics and assign someone to review outputs before every deployment.

Part 8 — Decision Heuristics & Rules of Thumb

Chain or agent? If the workflow steps are always the same in the same order → Chain. If the task requires the model to reason about which tools to use → Agent.

RAG or fine-tune? Ask: "Does the model lack information or behaviour?" Information → RAG. Style/tone/domain instinct → Fine-tune. Often both are needed.

Is loss enough? For supervised models: yes, it's the primary signal. For any generative model: no — you must inspect actual outputs at regular intervals.

Checkpoint frequency? Balance storage cost vs recovery granularity. For multi-hour runs: every 4–10 epochs. The best model is often not the final checkpoint.

Registry promotion sign-off? Minimum three roles: data scientist (quality), ML engineer (deployment), business owner (client fit). Never a single role alone.

Agent Tracer rule: If any step in a Trace shows None or an empty value as input to a downstream step — and that step reports success — the validator logic is broken, not the upstream step.

Qualitative evaluation frequency? Before every Registry promotion. Not a one-time pre-launch activity — it is ongoing monitoring.

S3 vs Artifact? If you cannot answer "which run, which dataset, which code produced this file?" from the file's metadata alone → it is not an Artifact, it is an orphan.

Part 9 — Terminology Glossary

RunAtomic unit of one experiment — one configuration executed once. A permanent, sealed record of all five reproducibility factors plus metrics.
ConfigStatic dictionary of hyperparameters captured once at init(). Answers "what did we try?" Does not change after the run starts.
MetricsDynamic values streamed continuously inside the training loop via log(). Answers "what happened?" Produces the loss curve, not just a final value.
ArtifactA versioned, context-bound file with full lineage to its producing run. Not just a saved file — it carries permanent links to the run, config, and metrics that created it.
LineageThe traceable chain linking a model artifact back to its training run, dataset version, and code state. Broken lineage = untraceable production model.
Diff patchW&B's automatic capture of uncommitted code changes at run time. Enables reproduction of any run: pull the Git commit + apply the patch.
CheckpointA mid-training model snapshot saved every N epochs. Enables crash recovery, protection against overfitting (peak may not be at final epoch), and branching for new experiments.
EpochOne complete pass through the entire training dataset. Training for 10 epochs means the model has seen every training example 10 times.
ProjectA collection of runs in W&B. The comparison and filtering layer — lets you plot all runs, filter by threshold, and sort by any metric to surface the best experiment.
Model RegistryThe curated promotion layer. Only models explicitly promoted by a human enter it. Tracks lifecycle: Staging → Production. Enables cross-team visibility and client audit trails.
SpanOne recorded step in an LLM chain or agent execution — captures input, output, start time, end time, and success/failure status.
TraceThe complete nested record of all Spans in one end-to-end execution. The Trace Timeline shows exactly where an agent or chain went wrong.
ChainAn LLM workflow where the steps are fixed and predetermined — always runs in the same order. Predictable. Easier to debug than agents.
AgentAn LLM workflow where the model itself decides which steps to take and in what order at runtime. Dynamic. Harder to debug — always requires Tracer in production.
Diffusion modelA generative model trained to reverse a progressive noising process. Forward pass: add noise until pure noise. The model learns to denoise. Inference: start from pure noise, iteratively remove noise to reveal an output image.
ConvergenceWhen a model's loss has stopped meaningfully improving. For generative models, convergence ≠ acceptable output quality — the two diverge early in training.
Supervised modelA model trained to map inputs to known, labelled outputs (e.g., classify this as category A or B). The correct answer is always known during training.
Generative modelA model trained to create new content (images, text, audio) that resembles the training data distribution. No single correct output — quality is qualitative.
